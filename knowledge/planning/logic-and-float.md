# 逻辑关系与浮时

> 可信度：📘 方法 + ✅ 部分实测（本次 41 项计划用 SS/FS + 延时复现月窗口，F9 后 0 偏差）
> 一句话：**日期由工期 + 逻辑 + 延时算出来，不是填进去的**；约束只用在外部定死的节点。

## 1. 四种关系

| 类型 | 含义 | 什么时候用 |
|---|---|---|
| `FS` 完成-开始 | 前驱完成后，后继才能开始 | 默认；设计→审查、到货→施工 |
| `SS` 开始-开始 | 前驱开始后过 `lag` 天，后继开始 | 分段流水：基础开工 6 个月后开始组塔 |
| `FF` 完成-完成 | 后继完成不早于前驱完成 + lag | 收尾类并行（少用） |
| `SF` 开始-完成 | 少用，生成器支持但不要主动用 | — |

延时 `lag` 在库里是**小时**（`TASKPRED.lag_hr_cnt`），生成器按 `天 × 8` 写入。

## 2. 用延时复现“月窗口”的做法（已验证）

给每个活动定目标 `start/finish`，再倒推每条关系的延时：

- `FS`：`lag = succ.start − pred.finish − 1`（负值则改用 `SS`）
- `SS`：`lag = succ.start − pred.start`

好处：不动约束、不写死日期，F9 自然落在窗口；坏处：逻辑是“为窗口服务”的，延时值要能解释（生产/海运周期、标段移交）。

> 判断标准：延时必须能说出一句现场理由（“铁塔生产+海运 5 个月”“基础完成 6 个月后组塔”）。说不出来就是硬凑。

## 3. 浮时

| 名称 | 字段 | 用法 |
|---|---|---|
| 总浮时 | `total_float_hr_cnt` | 0 = 关键；负 = 违反约束；正 = 可延误天数 |
| 自由浮时 | `free_float_hr_cnt` | 不影响任何后继的余量 |

- 关键活动很多不一定是错：控制性计划大量用延时链时，关键路径会很长。
- 负浮时先查：`must finish by`、`CS_MSO` 约束、开口活动、跨项目关系。
- 浮时是 F9 算的，**不要写进 CSV**。

## 4. 约束的使用边界

- 只用 `CS_MSO`（Must Start On）锁“外部定死”的点：政府批复、设备到货、投运窗口。
- 不要给每个活动都加约束：那等于把 CPM 变成横道图，浮时全失真。
- 约束会“压掉”该活动的浮时，并在负浮时排查时优先怀疑。

## 5. 里程碑

- 0 工期 + `FS`：落在后继工作日。
- 固定日期：`CS_MSO`；或改用 `TT_StartMile`（见 `ui/scheduling-f9.md`）。
- 不要为了“好看”加一堆里程碑；里程碑应当对应合同/验收节点。
